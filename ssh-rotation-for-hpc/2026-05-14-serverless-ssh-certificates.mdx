When our organisation mandated Single Sign-On (SSO) for all infrastructure access, I faced an immediate architectural conflict with our High-Performance Computing (HPC) cluster. Historically, developer access to the `science-surge` cluster relied on traditional, permanent SSH public keys appended to `authorized_keys` files. This legacy approach fundamentally expects static credentials, directly contradicting the dynamic, verifiable authentication required by modern corporate security policies. 

The organisational requirement was clear: all access must be authenticated via AWS SSO. However, the operational constraint was equally rigid: any solution had to support native SSH tooling. Our engineering team relies heavily on remote development environments, specifically Cursor and Visual Studio Code (VS Code), which use the SSH protocol to sync file systems and execute language servers directly on the remote compute nodes. Standard SSH proxy wrappers or proprietary web terminals were not viable, as they break the seamless remote IDE experience. I needed a mechanism to bridge AWS SSO with the native OpenSSH daemon running on our cluster.

## The Concept: OpenSSH Certificates

The solution to bridging SSO with native SSH lies in [OpenSSH Certificates](https://www.openbsd.org/papers/bsdcan-sign.html) [1]. Instead of configuring a server to trust a disparate collection of individual public keys, I configured the OpenSSH daemon to trust exactly one cryptographic identity: the Certificate Authority (CA).

Under this paradigm, when a developer requires access, they present their standard public key to the CA. If the developer successfully authenticates, the CA cryptographically signs their public key, returning a time-bound certificate. This certificate embeds critical metadata, most notably a strict expiration timestamp and the authenticated identity of the principal. The developer then presents this signed certificate to the target server. Because the server inherently trusts the CA, it implicitly trusts any valid, unexpired certificate signed by it. This architectural shift moves the security boundary; rather than managing keys on the compute nodes, I only needed to secure the CA and its issuance process.

## Architecture Breakdown: A Serverless CA

To implement this without introducing a new stateful infrastructure component to manage, I designed a serverless SSH Certificate Portal on AWS. This approach aligns with our pragmatic goal of minimising ongoing operational maintenance.

The architecture operates through the following sequence:

1. **Authentication:** The developer authenticates using their existing AWS SSO credentials via the AWS Command Line Interface (CLI). This satisfies the organisational requirement without introducing a separate identity provider.
2. **Invocation:** The developer invokes a specific AWS Lambda function (`cluster-ssh-sign-cert`), passing their public key as a JSON payload.
3. **Verification:** The Lambda function, executing under a highly restricted Identity and Access Management (IAM) role, verifies the caller's SSO identity. It then cross-references the submitted public key against a predefined registry maintained in AWS Systems Manager (SSM) Parameter Store to ensure the key belongs to the authenticated user.
4. **Signing:** Upon successful verification, the Lambda function retrieves the 4096-bit RSA CA private key, which is securely stored in AWS Secrets Manager. It uses an embedded OpenSSH layer to sign the developer's public key.
5. **Issuance:** The function returns a certificate configured with a strict 8-hour Time-To-Live (TTL).

On the cluster side, the configuration footprint is microscopic. The `/etc/ssh/sshd_config` file requires only two modifications: setting `TrustedUserCAKeys` to point to the CA's public key, and explicitly enabling RSA signatures (`PubkeyAcceptedAlgorithms +ssh-rsa`), which are disabled by default in modern OpenSSH distributions but required for our 4096-bit RSA CA.

## Production Realities and Trade-offs

While this architecture elegantly resolves the SSO requirement, it introduces specific organisational and operational trade-offs. 

Firstly, by moving the authentication pathway through AWS Lambda and Secrets Manager, I introduced a hard runtime dependency on the AWS control plane for SSH access. If the `eu-west-2` region experiences an Application Programming Interface (API) disruption, developers cannot obtain new certificates. However, because the certificates are valid for 8 hours, active sessions and any new connections made with a cached, unexpired certificate remain unaffected. I assessed this as an acceptable trade-off for the substantial reduction in static credential risk.

Secondly, I observed a minor latency penalty during the issuance phase. A "cold start" Lambda invocation takes approximately 400 milliseconds, whereas a "warm" invocation completes in under 50 milliseconds (see Table 1). Given that developers only execute this script once per working day, this latency is imperceptible in practice and represents a negligible constant factor compared to the overhead of managing static keys.

## Conclusion

By adopting OpenSSH certificates and wrapping the issuance process in a serverless AWS architecture, I successfully aligned our HPC cluster access with strict corporate SSO mandates. This approach eliminated the substantial security risks associated with static SSH keys, reducing our credential footprint on the servers to a single, easily rotated CA key (see Table 1). 

Most importantly, this security enhancement did not degrade the developer experience. Because the system outputs standard SSH certificates, engineers continue to use Cursor, VS Code, and standard terminal multiplexers without friction. In practice, treating infrastructure access as a dynamic, verifiable event rather than a static configuration state provides a robust foundation for secure, scalable remote development.
