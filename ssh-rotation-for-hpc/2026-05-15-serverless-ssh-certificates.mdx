While my primary engineering focus is on geospatial data architecture, I have a "second life" in my current role: maintaining the High-Performance Computing (HPC) cluster for our science team. This dual responsibility often forces me to bridge the gap between strict corporate IT policies and the pragmatic, high-friction realities of research infrastructure.

When our organisation mandated Single Sign-On (SSO) for all infrastructure access, I faced an immediate architectural conflict with our HPC cluster. Historically, developer access to our primary compute cluster relied on traditional, permanent SSH public keys. In a traditional setup, a developer generates a cryptographic key pair on their laptop. The "private" half stays hidden on the laptop, while the "public" half is copied onto the remote server's `authorized_keys` file. When the developer tries to log in, the server uses that public key to verify that the developer holds the corresponding private key. 

This legacy approach fundamentally expects static, unchanging credentials. If an engineer leaves the company or loses their laptop, administrators must scramble to manually delete that public key from every server it was ever copied to. This directly contradicts the dynamic, verifiable authentication required by modern corporate security policies, which demand that access is tied to a central identity provider (like Okta or Azure AD) and can be revoked instantly.

The organisational requirement was clear: all access must be authenticated via our central AWS SSO system. However, the operational constraint was equally rigid: any solution had to support native SSH tooling. Our engineering team relies heavily on remote development environments, specifically Cursor and Visual Studio Code (VS Code). These tools use the standard SSH protocol behind the scenes to sync file systems and execute language servers directly on the remote compute nodes. Standard enterprise workarounds—like clunky web-based terminals or proprietary proxy wrappers—were not viable, as they break the seamless remote IDE experience. I needed a mechanism to bridge the modern world of AWS SSO with the decades-old native OpenSSH daemon running on our cluster.

## The Concept: OpenSSH Certificates

The solution to bridging SSO with native SSH lies in a feature that has been built into the protocol for years: [OpenSSH Certificates](https://www.openbsd.org/papers/bsdcan-sign.html) [1]. 

To understand certificates, think of how a traditional office building works. Under the old "public key" model, every single door lock in the building must be manually programmed with a list of every employee's unique house key. If you hire someone, you update every lock. If you fire someone, you update every lock. 

The "certificate" model introduces a security guard—the Certificate Authority (CA). Instead of configuring the server (the door lock) to trust a disparate collection of individual public keys, I configured the OpenSSH daemon to trust exactly one cryptographic identity: the CA.

Under this paradigm, when a developer requires access, they present their standard public key to the CA. The CA acts as the security guard. It asks, "Who are you?" If the developer successfully authenticates (in our case, via SSO), the CA cryptographically signs their public key, returning a time-bound "certificate." This certificate is like a visitor's badge. It embeds critical metadata, most notably a strict expiration timestamp (e.g., valid for the next 8 hours) and the authenticated identity of the principal (e.g., "Developer A").

The developer then presents this signed certificate to the target server. Because the server inherently trusts the CA, it implicitly trusts any valid, unexpired certificate signed by it. This architectural shift fundamentally moves the security boundary. Rather than managing a sprawling list of keys across hundreds of compute nodes, I only needed to secure the CA and its issuance process. If an employee leaves, their SSO is disabled, they cannot get a new certificate, and their old certificate expires harmlessly at the end of the day.

## Architecture Breakdown: A Serverless CA

To implement this without introducing a new, stateful infrastructure component that our small team would have to monitor and patch, I designed a serverless SSH Certificate Portal on AWS. This approach aligns with our pragmatic goal of minimising ongoing operational maintenance by relying on managed cloud services.

The architecture operates through the following sequence:

1. **Authentication:** The developer authenticates using their existing AWS SSO credentials via the AWS Command Line Interface (CLI). This ensures they have an active session with our corporate identity provider. This satisfies the organisational requirement without forcing us to build a separate login portal.
2. **Invocation:** Once authenticated, the developer runs a script that invokes a specific AWS Lambda function. AWS Lambda is a compute service that lets you run code without provisioning or managing servers. The developer passes their public key to this function as a JSON payload.
3. **Verification:** The Lambda function executes under a highly restricted Identity and Access Management (IAM) role. It first verifies the caller's SSO identity to ensure they are who they claim to be. It then cross-references the submitted public key against a predefined registry maintained in AWS Systems Manager (SSM) Parameter Store [2] (a secure key-value store). This check ensures the submitted key actually belongs to the authenticated user and hasn't been swapped out.
4. **Signing:** Upon successful verification, the Lambda function needs to act as the Certificate Authority. It retrieves the CA's highly sensitive 4096-bit RSA private key, which is securely locked in AWS Secrets Manager [3]. Because AWS Lambda's default execution environment is stripped down and does not include standard SSH utilities, I attached a custom AWS Lambda Layer. A Layer is simply a ZIP archive that contains additional code or data; in this case, it contains the native `ssh-keygen` binary. The function invokes this binary, feeding it the CA's private key, to cryptographically sign the developer's public key.
5. **Issuance:** The function returns the newly minted certificate, configured with a strict 8-hour Time-To-Live (TTL).

On the cluster side, the configuration footprint is microscopic. The `/etc/ssh/sshd_config` file—the configuration file for the SSH daemon running on the servers—requires only two modifications. First, setting `TrustedUserCAKeys` to point to the CA's public key. Second, explicitly enabling RSA signatures (`PubkeyAcceptedAlgorithms +ssh-rsa`). Modern OpenSSH distributions disable RSA signatures by default due to historical associations with the weak SHA-1 hashing algorithm; however, because our CA specifically generates mathematically strong 4096-bit RSA keys, we must explicitly re-enable this protocol support to allow the daemon to validate the certificates.

## Production Realities and Trade-offs

While this architecture elegantly resolves the SSO requirement, it introduces specific organisational and operational trade-offs that must be acknowledged. 

Firstly, by moving the authentication pathway through AWS Lambda and Secrets Manager, I introduced a hard runtime dependency on the AWS cloud control plane for SSH access. If our primary AWS region experiences an Application Programming Interface (API) disruption, developers cannot obtain new certificates. However, because the certificates are valid for 8 hours, active sessions and any new connections made with a cached, unexpired certificate remain unaffected. I assessed this as an acceptable trade-off for the substantial reduction in static credential risk.

Secondly, I observed a minor latency penalty during the issuance phase. When an AWS Lambda function has not been called recently, it must boot up an execution environment from scratch—a phenomenon known as a "cold start." A cold start Lambda invocation takes approximately 400 milliseconds, whereas a "warm" invocation (reusing an existing environment) completes in under 50 milliseconds (see Table 1). Given that developers only execute this script once per working day to grab their daily certificate, this half-second latency is imperceptible in practice and represents a negligible constant factor compared to the manual overhead of managing static keys.

## Conclusion

By adopting OpenSSH certificates and wrapping the issuance process in a serverless AWS architecture, I successfully aligned our HPC cluster access with strict corporate SSO mandates. This approach eliminated the substantial security risks associated with static SSH keys, reducing our credential footprint on the servers to a single, easily rotated CA key (see Table 1). 

Most importantly, this security enhancement did not degrade the developer experience. Because the system outputs standard SSH certificates, engineers continue to use Cursor, VS Code, and terminal tools like `tmux` (which keep long-running jobs alive even if a laptop disconnects) without any friction. In practice, treating infrastructure access as a dynamic, verifiable event rather than a static configuration state provides a robust foundation for secure, scalable remote development.
